# Phase 5 Proof2Test evaluation protocol

Falsifiable question: for a replay-validated Doppelgänger witness and a separately declared target output, can an exported test reproducibly reject a defective transformation and accept a corrected transformation on that same input? Null explanation: the exported test merely restates `BLIND_SPOT_FOUND`, uses the witness's observed output as its oracle, or cannot execute outside the development checkout. The test must instead compare the target's actual output bag with an independently declared expected bag and re-evaluate the source invariant on that output in DuckDB.

Scope: one synthetic table, finite INTEGER/DATE domains, at most three bag rows, Phase 4 scalar-aggregate invariant and existing-test fragment. The target is a same-schema, single-table read-only SELECT with direct columns, optional `GREATEST(INTEGER_column, 0)`, and at most one existing guarded filter. dbt export is narrower: nonempty, non-NULL INTEGER rows and a single local `ref` parent. NoUndo export, arbitrary model graphs, production connections and LLM-generated expectations are excluded.

Primary oracle: independent DuckDB replay of the source witness (including legal schema, all original tests, invariant SQL, recorded evaluations and replay SQL), then DuckDB execution of the exported fixture against each supplied target. The expected output bag is a separate contract, not computed from either target. The real dbt control uses dbt Core unit tests with inline `given`/`expect` rows on dbt-duckdb. Negative controls tamper rows, SQL, evaluations and fixture bytes, and mutate target SQL into unsupported or behaviorally wrong forms. The corrected and defective example are distinct supplied SQL files; this one example cannot establish a general repair rule.

Run the generated pytest test twice from a fresh Wheel installation: defective must exit 1 for `target output bag differs`; corrected must exit 0 with one passed test. Run the dbt unit test on a local isolated project with an existing empty parent relation: defective must fail and corrected must pass. Regenerate artifacts and compare bytes; reject tampering. Record exact source commit, input and output hashes, versions, operating system, exit codes and elapsed times. Raw run directories and logs stay under ignored `research/runs/local/`; publish only a sanitized summary after a clean committed run. Timing is descriptive one-run metadata, not a method comparison; there is no variance estimate or performance conclusion.

Competing work: [dbt Core unit tests](https://docs.getdbt.com/docs/build/unit-tests) already provide given/expect fixtures; [Hypothesis](https://hypothesis.readthedocs.io/) generates and shrinks property-based examples; [Spec-Lock-Diff](https://github.com/miloskimatheus/spec-lock-diff/) and [XData](https://arxiv.org/abs/1411.6704) cover mutation-oriented test adequacy and SQL test-data generation. The question here is narrower: faithful export of an independently replayed DataProof witness plus an explicit target expectation. No fair head-to-head comparison or novelty conclusion is claimed.
