# P2-R1 preregistration: invariant guidance versus seeded random generation

Status: **implementation draft, not executed**. This protocol is separate from Phase 6. The ten case inputs in `research/p2_r1/cases/` are frozen design inputs. Their expected statuses below are hypotheses, never filtering criteria. No outcome has been checked for these cases as part of implementation.

## Question, comparison, and scope

Within the present one-table finite Doppelgänger fragment, does invariant-guided Z3 search offer a practically meaningful advantage over the existing unguided seeded random sampler in finding **DuckDB-confirmed** datasets satisfying all existing tests as SQL TRUE and a separately declared invariant as SQL FALSE? H0: no practically meaningful advantage under this protocol. This is not a novelty comparison with XData, ADUSA or other query-aware database generation.

Only the existing `doppel_solver.search`, `doppel_reference.reference_search`, `reference_enumerator.all_worlds`, `doppel_replay.validate`, and `run_doppelganger.random_baseline` perform search/evaluation. The P2-R1 worker isolates those existing calls; the harness records trials. It does not alter production algorithms or the accepted SQL grammar. All assertions are scalar aggregates with one optional guarded predicate. Source tables have at most three bag rows, four columns, four declared values per column, one to four tests, and one independent invariant. Each invariant rationale is an *input policy assertion*, not verified business truth.

## Execution and accounting, subject to a separate approval

Execution command, **not to be run during harness implementation**: `PYTHONPATH=src:. .venv/bin/python -m research.benchmarks.p2_r1 --execute --output research/runs/local/p2-r1-<run-id>`. The runner requires an exact frozen case set, a clean committed worktree, a new output directory under the ignored local run tree, and an explicit `--execute` flag. Without that flag it only parses the cases and calculates analytical bounds.

For each case, run the existing exhaustive DuckDB reference once in a fresh process, with a 60-second parent-enforced wall cap. Record status, legal and test-passing world counts, full-enumeration elapsed time, and witness size when present. This is a ground-truth control under the declared finite model, not equal-work search timing. If it errors/times out, retain `REFERENCE_UNRESOLVED` via its recorded exception/timeout status; do not count a positive as oracle-confirmed or discard the case.

Run 50 fixed random seeds, integer 0 through 49, at most 200 **raw** draws each, with checkpoints at 20, 100 and 200. A draw chooses a row count uniformly from 0..max_rows, then each declared domain value uniformly with replacement, exactly as in the existing random baseline. Illegal worlds are counted as draws but not evaluated in DuckDB. Record raw draws, legal draws, test-passing draws, DuckDB evaluations, first hit, status, elapsed time and witness size. A random miss is `NO_WITNESS_WITHIN_BUDGET`, not a bounded-no-blind-spot or inconsistent-test conclusion. Random has an 11-second internal post-load soft deadline and the common 12-second parent hard cap; the 200-draw cap may stop it sooner. These are *additional restrictions*, not computational parity with SMT.

Run 50 fresh-process Z3 timing repetitions per case. Z3's search is deterministic for a fixed case; these repetitions are **not independent discovery trials**. The solver keeps its 10,000-ms timeout and 256-MiB Z3 memory parameter. Every candidate receives independent DuckDB `validate` before credit. Record bounded statuses, reason codes, row-minimality flag, size, elapsed time, peak process RSS and false claims. The 12-second parent cap applies from process launch through parsing, search and validation. Parent timeouts and worker exceptions receive distinct status records. Z3 solver memory is bounded by its Z3 setting; random has **no equivalent enforced memory cap**. Both methods' observed peak RSS is reported with platform-specific units. This memory asymmetry prevents any equal-resource claim.

Launch each method in the same process regime, with **no excluded warm-ups**. Alternate Z3-first and random-first order across seed indices; reference runs separately first. Parent wall time includes process startup; worker wall time excludes startup and is recorded separately. The harness never counts one SMT check as one random DuckDB evaluation. Reference's all-world evaluation time is reported separately, including any case on which it is faster than Z3.

Raw machine-readable `manifest.json` and `trials.jsonl` remain only in `research/runs/local/`. Records have case IDs and SHA-256 hashes, code SHA, UTC time, versions, fixed budgets, method, trial index, statuses, counts and timings. Neither worker stdout/stderr nor exception messages are published. The allow-list sanitizer is applied before local trial writing and must be used for any later public summary. No file under `research/runs/published/` is created or overwritten by this harness. A public summary requires a separately reviewed, real clean run; never substitute hypotheses for results or edit timestamps. The raw local record is not an independently downloadable archive.

The reviewed case SHA-256 values are pinned in `research/benchmarks/p2_r1.py`; a changed input requires a new explicit preregistration review before execution. The initial manifest always says `INCOMPLETE`. Only an atomically created `completion.json` with `RECORDING_COMPLETE`, the exact 1,010-record count and a trial-stream SHA-256 marks recording complete. The runner verifies one reference, 50 Z3 and 50 random records per case, unique trial keys, seed coverage, case hashes and oracle consistency after flushing the stream. A partial/interrupted run stays incomplete; there is no resume or overwrite. Completion says only that records are intact, **not** that results are valid: exceptions, timeouts, inconclusive results and disagreements remain in the data and must be analyzed.

## Decision rules and limitations

Primary endpoint: per-case DuckDB-confirmed discovery by the 12-second parent cap across the eight **hypothesized** satisfiable cases, reported alongside random checkpoints. For each such case, random discovery proportion is confirmed hits divided by all 50 prespecified seeds; Z3 discovery is described as a deterministic-case result, with its 50 runs reported as timing/stability repetitions, **not** 50 independent Bernoulli observations. The descriptive primary gap is the unweighted mean across the eight case-specific differences (Z3 discovery indicator minus random proportion). The proposed practical threshold is **20 percentage points**, fixed before execution, not an observed effect. It is crossed descriptively only if the primary gap is at least 0.20; this is not a population hypothesis test or novelty claim. Report each case, the gap, and timing/failure distributions even if the threshold is not crossed. Do not construct a case/seed-aware confidence interval or p-value for a population of SQL cases: these eight cases were hand-designed, not sampled. As exploratory seed-sampling sensitivity only, report each random proportion with a 95% Wilson score interval using z=1.959963984540054, denominator 1+z²/50, center (p+z²/100)/denominator and half-width z*sqrt(p*(1-p)/50+z²/(4*50²))/denominator. The 50 fixed seeds are not a random sample of real pipelines, so even these intervals are conditional/model-based and may be wide or uninformative; do not aggregate them into an inferential interval for the primary gap.

The primary set remains the eight IDs above regardless of observed outcomes. The completed oracle independently labels each case within the finite model. If an expected-positive case is oracle-negative, preserve it in the eight-case descriptive table, mark the preregistered endpoint as contradicted/noninterpretable for an advantage claim, and do not replace it. If the oracle is unresolved, retain the case in the denominator and mark its contribution unresolved; report the attainable range of the eight-case gap by assigning that case's unknown confirmed-discovery contribution its logical extremes rather than silently excluding it. All ten cases and every trial remain visible. A Z3 false claim or conflict with a resolved oracle triggers correctness investigation and suspends advantage interpretation. Negative M1/I1 cases are controls, not silently promoted into the primary set if outcomes differ. No reclassification or exclusion may be chosen after seeing favorable results.

Secondary outcomes: time-to-confirmed witness (including all failures as censored), row size and oracle minimum row size, legal/test-passing random candidate rates, exceptions, soft/hard timeouts, inconclusive solver outcomes, false claims, memory metadata, and random/exhaustive wins or ties. Do not report success-only mean times as overall speed. Any solver/exhaustive status disagreement, DuckDB-invalid candidate, or claimed witness under an oracle-confirmed negative case is a correctness event requiring investigation before scientific interpretation. A random miss on a positive case is an allowed budget miss, not a disagreement; random cannot certify negative statuses.

Threats: hand-selected tiny cases, uncertain rarity before enumeration, fixed domains and DuckDB version, deterministic Z3 timing noise, unequal unit work, shared schema parser/`legal_world` between methods, and DuckDB reference and candidate validator sharing the same SQL engine. DuckDB executes original SQL independently of Z3, but **not** independently of the shared input schema/constraint model; correlated errors remain possible. Existing NULL/bag/constraint differential tests reduce but do not remove that risk. E1 remains in the study even though the published Phase 4 record shows random succeeded in all five earlier trials. Never pick or drop cases based on favorable results.

Study execution, interpretation and publication require new authorization after review of the harness, fixtures, tests and clean committed protocol. No Phase 6 work is implied.
